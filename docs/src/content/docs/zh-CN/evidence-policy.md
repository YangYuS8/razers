---
title: "上游证据政策"
description: "复用上游成果、调查事实冲突，并区分实验性支持与实机验证。"
---

RazeRS 应能由小型社区维护。已有开源驱动的实现和测试经验，在来源、含义与许可清晰时，
就是可复用的工程证据；不要求维护者购买并重复测试每个型号。

## 证据能支持什么

固定版本的上游实现可提供设备标识、连接与协议参数、能力范围、灯光几何、命令行为、
时序、quirks 和预期响应。可据此生成候选清单、实现 Rust 类型化驱动、构造黄金数据包
与无硬件回放，并在满足下面条件时发布 `experimental` 能力。

RazeRS 实机测试有价值，但不是每项实现的前置条件。`verified` 专门表示某个 RazeRS
构建在有记录的平台、连接、固件和能力上通过测试。

## 实验性能力的门槛

1. 每项关键事实都指向准确仓库、提交、文件和符号。
2. 成熟上游实现明确支持该设备，或两个独立实现对关键事实达成一致。
3. 编码、响应校验、限制和失败路径具有本地单元/回放测试。
4. 实际 I/O 限于精确匹配的厂商接口。
5. 在更强证据或社区反馈建立安全默认值前，可撤销写入需要显式实验性启用。

持久存储、固件、引导程序以及尚未理解的原始写入，不能仅凭目录元数据开启。

## 处理差异

没有任何来源具有全局优先级。应按字段评估相关性：灯光实现可能更了解矩阵，
设备驱动可能更了解 DPI 范围与响应时间。出现差异时：

1. 先统一名称、单位、矩阵方向、连接模式、硬件修订和固件范围。
2. 检查精确源码、提交历史、Issue、PR、发行说明、测试和已脱敏轨迹。
3. 寻找其他独立实现或厂商文档。
4. 在清单或来源记录中保留每个声明及最终选择的理由。
5. 真实变体建模为不同连接、修订或 quirks，不强行统一。
6. 未解决时只禁用受影响字段/能力的真实操作，保留争议记录。

一致性不是自动合并规则；差异意味着需要调研，不意味着要求维护者购买设备。

## CLI 评估流程

```bash
cargo run -p razers-cli -- --lang zh-CN upstream assess 1532:0099
cargo run -p razers-cli -- --lang zh-CN upstream shortlist
cargo run -p razers-cli -- --lang zh-CN upstream conflicts
```

结果分别报告来源覆盖、名称、类别、矩阵尺寸及 OpenRGB/iRazer 协议参数的一致性。
`corroborated` 表示至少两个目录收录且可比较的重要字段无冲突；`needs-research`
表示类别、矩阵或协议存在重要差异；`single-source` 表示只有一个目录收录。

名称差异会保留，但不单独阻塞候选，因为拼写、品牌和修订后缀需要规范化。
`not-comparable` 表示某侧缺少事实，不表示一致。相互印证仅是调研候选，不是 RazeRS
`experimental` 或 `verified` 声明，仍须满足上述门槛。

## 面向用户的支持声明

- `detected`：标识已知，但没有 RazeRS 控制命令。
- `experimental`：有证据支持的实现与回放测试；实机测试可选，限制必须可见。
- `verified`：存在针对指定平台、固件、连接与能力的 RazeRS 实机记录。
- `regressed`：曾经工作的行为现在失败。
- `unsupported`：证据确认在指定范围内不可用。

社区验证可以增加覆盖并提升状态，但缺少 RazeRS 实机记录不能抹除可信上游结果或强迫重复研究。
